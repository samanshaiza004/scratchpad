## Invalidation and accessibility details

The app-level theme test is meaningful: `scratchpad_theme_select` re-describes the root, then the test confirms retained identity, paint changes, and zero added layout/measurement for the tested color switch. The full-scene test repeats the no-layout assertion for Flat, Relief, and Warm while preserving modal/editor semantics. The evidence does **not** establish the requested exact domain diff or post-switch idle on that app path. Current paper and Cool Light editor-padding dimensions are both 10 px, so no selected Scratchpad theme exercises a theme-driven metrics change (`themes/scratchpad-paper.json:198-207`; `themes/scratchpad-cool-light.json:26-27`). Alicorn’s generic environment contract treats theme-ID changes as Paint-only and text scale as Metrics + Typography (`runtime/style.odin:5-25`; `tests/style_environment.odin:90-108`).

Scratchpad inherits Alicorn’s host accessibility preferences by default and its test passes all four appearance booleans through workbench and nested editor scopes. Alicorn’s built-in controls enforce 4.5:1 text and 3:1 focus/selection fallbacks, plus non-color selected markers; Windows and macOS host preference monitoring is documented. `frontends/alicorn/main_test.odin:338-458`; `docs/themes.md:58-106`; `runtime/accessibility_appearance_test.odin:35-70`.

At the audited baseline, Scratchpad-only accessibility overrides were not saved: the version-1 preference struct contained theme/font/zoom fields only, and the Accessibility page updated app memory without calling the preference saver (`frontends/alicorn/theme_preferences.odin:16-22`; `frontends/alicorn/settings_surface.odin:204-228`). Also, Alicorn’s contrast guarantees are strongest for built-in recipes. App-authored extension colors do not receive the built-in recipe contrast fallback, so the “custom theme cannot hide required state” guarantee is proven for Alicorn controls, not all Scratchpad custom paint (`runtime/style.odin:397-408,458-496`; `runtime/style_resolution.odin:5-10`). The new syntax token palettes were selected for readable contrast on the shipped editor surfaces, but this does not add generic contrast enforcement to app extension roles.

## Audit result

The ordinary theme-selection and preference-file paths are substantially implemented. Acceptance remains incomplete on the evidence boundary: no macOS theme run/capture, no process-restart-without-session proof, no app-level trace/inspector record of exact invalidation domains and idle resumption, and no end-to-end provenance assertion for Scratchpad-authored visual parts. The remaining local syntax/Markdown paint palette was a concrete Alicorn-style ownership gap; custom file themes themselves are not currently a Scratchpad product feature.

## Implementation follow-up

In the current working tree, code syntax paints now resolve named `app.scratchpad.syntax.*` extension roles from the active compiled theme, with Alicorn core-role fallbacks for a theme missing one of those optional extensions. Warm and Cool Light author separate syntax token palettes. The modal backdrop is now a namespaced theme role used by all editor, workspace, settings, and confirmation overlays. The former duplicated hard-coded modal color remains only as a defensive fallback if a registered theme lacks that role. The introductory theme documentation describes these mappings.

This addresses the concrete app-local color-table gap without adding another runtime theme mechanism. Alicorn's theme compiler regenerated the static theme data, and the native build succeeded with the exact pinned Alicorn checkout, producing `out/alicorn/scratchpad-alicorn`.
